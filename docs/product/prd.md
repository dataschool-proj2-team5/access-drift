## 1. 제품 개요

Access Drift는 SCIM/IdP로는 관리된 것처럼 보이지만 실제 SaaS 권한과 NHI 접근 경로에는 남아 있는 접근권한 드리프트를 탐지하고, 그 접근 경로가 어떤 민감 자산에 닿는지 설명한 뒤, 보안팀이 검토와 조치까지 이어갈 수 있도록 돕는 보안 운영 제품이다.

---

## 2. 문제 정의

대기업은 Entra ID, Okta 같은 IdP와 SCIM으로 계정 라이프사이클을 중앙에서 관리한다. 퇴사·팀 이동·외주 종료 시 IdP에서 처리하면 접근이 차단됐다고 판단한다. 하지만 실제로는 그렇지 않은 경우가 구조적으로 발생한다.

**이유 1 — SCIM 미지원 플랜**  
대다수 SaaS는 하위 플랜에서 SCIM을 지원하지 않는다. Figma는 Organization 이상, GitHub는 Enterprise Cloud, Vercel·Render는 월 $499 이상 플랜에서만 SCIM을 제공한다. 즉 IdP에서 계정을 껐어도 SaaS에서 자동 해제가 애초에 불가능한 구조다.

**이유 2 — SCIM 동기화 오류·중단**  
SCIM 연결에 사용하는 API key가 만료되거나 설정이 변경되면 동기화가 조용히 멈춘다. 보안팀은 "SCIM이 있으니 됐겠지"라고 믿는 사이 계정이 살아 있다. Stitchflow 2026 SCIM Gap Report에 따르면 Okta를 사용하는 조직에서도 조직당 평균 422개의 identity/access gap이 관측된다.

**이유 3 — SCIM 이후에도 SaaS 내부 권한은 별도**  
SCIM이 계정 비활성화를 처리해도 SaaS 내부 role, 그룹 멤버십, 프로젝트 접근 권한은 자동으로 해제되지 않는다. Atlassian Guard 없이 SSO만 있으면 SaaS 자체 계정 로그인이 여전히 가능하고, 개인 이메일로 초대된 외부 협력자는 IdP 관리 범위 밖이라 오프보딩 프로세스에서 아예 누락된다.

**NHI는 사람 계정과 독립적인 별개 경로다**  
API token, Service Principal, OAuth App, integration credential은 인사 오프보딩 프로세스에 포함되지 않는다. 생성자가 퇴사해도 소유권이 이전되지 않고, 만료·삭제 정책이 없으면 민감 자산에 접근 가능한 상태가 수개월~수년간 유지된다. 쿠팡 3,370만 건 유출(2025)이 이 구조의 실제 결과다.

> **핵심 질문:** SCIM/IdP 기준으로는 정리된 것처럼 보이지만, 실제 SaaS/NHI 접근 경로에는 어떤 권한이 남아 있고, 그 권한은 어떤 민감 자산에 닿는가?

## 3. 타깃 사용자 & Pain

**1차 사용자**

**보안팀 운영 담당자 (Pattern 1 주체)**  
퇴사·외주 종료 후 SaaS 권한이 실제로 해제됐는지 확인하고 조치하는 사람.
- 핵심 질문: SCIM이 있는데 왜 이 계정이 아직 이 workspace에 있지? 이 권한이 어떤 자산에 닿는가?
- 현재 방식: SaaS별 관리자 콘솔을 하나씩 수동 확인. 조치 요청은 메신저로 보내고 결과는 별도 기록. 누락이 생기고 감사 대응 시 근거가 없다.

**IAM 담당자 (Pattern 2 주체)**  
Entra ID, App Registration, Service Principal, SCIM 정책을 관리하는 사람.
- 핵심 질문: 이 SP의 담당자가 누구인가? 이 credential이 활성 상태인 이유가 있는가?
- 현재 방식: Azure 콘솔과 스프레드시트로 수동 추적. SP owner가 퇴사한 경우 담당자를 파악할 방법이 없고, 어떤 자산에 영향을 주는지 설명하기 어려워 조치 요청 자체가 지연된다.

**2차 사용자:** 내부 감사 담당자, 컴플라이언스 담당자, 데이터/플랫폼 owner

**공통 Pain**
- "SCIM이 있으니 됐겠지"라는 믿음과 실제 접근 상태 사이의 gap을 확인할 방법이 없다
- 단순히 계정이 남아있다는 사실이 아니라 그 계정이 어떤 민감 자산에 닿는지 알기 어렵다
- 탐지 이후 담당자 확인, 권한 회수 요청, 티켓 작성, 감사 로그 기록이 수동으로 끊긴다
- 잔존 접근 경로가 발견되지 않은 채 수개월 방치될 수 있다

## 5. MVP 범위

**탐지 패턴 2가지에만 집중한다.**

**타겟 포지셔닝:** 커머스·금융·반도체·제조 등 다산업군 대기업을 대상으로 한다. 데모는 커머스 대기업 단일 시나리오로 구성한다.

**Pattern 1 — SCIM 사각지대 SaaS Access Drift**  
SCIM이 있어도 SaaS 권한이 실제로 해제되지 않는 케이스를 탐지한다. 원인은 세 가지다: SCIM 미지원 플랜, SCIM 동기화 오류·중단, SCIM 이후에도 별도로 남는 SaaS 내부 권한. guest·external collaborator는 이 중 하나의 케이스다.

> 예시: SCIM 동기화가 중단된 사이 퇴사자 계정이 고객 데이터가 포함된 workspace에 접근 가능한 상태로 남아 있다.

**Pattern 2 — NHI Access Drift**  
퇴사자가 생성하거나 접근했던 NHI(token, credential, integration)가 오프보딩 이후에도 폐기되지 않고 민감 자산에 접근 가능한 경우

> 예시: 퇴사자가 생성한 integration credential이 오프보딩 이후에도 활성 상태로 남아 production 관련 자산에 접근 가능하다.

## 6. Non-goals

전체 자산관리 시스템, 전체 SaaS 계정 인벤토리, 범용 SSPM/CIEM/SIEM, 전체 NHI 라이프사이클 관리, 데이터 유출 여부 확정 판단, 무승인 자동 조치, 영향 범위 계산, 메타데이터 기반 복잡한 위험 점수화

## 7. 핵심 사용자 흐름

**위험 검토 흐름**  
보안팀 → 대시보드 접속 → 리스크 카드 확인 → 접근 경로 검토 → 조치 선택(검토 요청 / 권한 회수) → 상태 업데이트 → 기록

**검토 요청 흐름**  
리스크 카드에서 검토 요청 선택 → 시스템이 Jira 티켓 초안 생성 → 보안팀 확인 후 생성 → 담당자 검토·승인 → 리스크 카드 상태 반영

**권한 회수 흐름**  
리스크 카드에서 권한 회수 선택 → 대상 시스템 API 호출(사람 계정: SaaS API / NHI: Azure 등 대상 시스템 API) → 결과 기록

**리스크 카드 상태 모델**  
`미처리` → `검토 중` → `조치 완료` / `리스크 수용` / `오탐`

## 8. 기능 요구사항

### 8.1 접근권한 드리프트 탐지

SCIM/IdP 상태와 SaaS/NHI 권한 상태를 비교해 드리프트를 탐지한다.

지원 드리프트 유형 (위협 모델 분류 기반):

*사람 계정 (패턴 1)*
- A-S1. 계정 잔존 `MVP` — SCIM 미지원 플랜 또는 동기화 오류로 IdP 비활성화 후에도 SaaS에 계정이 남아 있는 상태
- A-S2. SaaS 내부 권한·멤버십 잔존 `MVP` — SCIM이 계정을 처리해도 SaaS 내부 role, 그룹 멤버십, 프로젝트 권한이 별도로 남아 있는 상태. guest·external collaborator 포함
- A-S3. 소유권·객체 잔존 `향후 고려` — 계정은 비활성화됐지만 해당 사람이 만든 자동화 규칙, 관리자 역할이 남아 있는 상태

*NHI (패턴 2)*
- B-S1. 소유자 불명확 NHI `향후 고려` — 생성자가 떠났거나 담당팀이 바뀌어 관리 주체가 불명확한 token, SP, OAuth App, service account
- B-S2. 퇴사 후 미폐기 NHI `MVP` — 사람 계정은 오프보딩됐지만 해당 사람이 생성·접근했던 NHI가 별도로 폐기되지 않은 상태

### 8.2 접근 경로 표시

탐지된 리스크에 대해 누가/무엇이 → 어떤 권한을 통해 → 어떤 자산에 접근 가능한지를 접근 경로로 표시한다.

```
SCIM 미관리 게스트 → SaaS 워크스페이스 멤버 → 프로젝트 권한 → 고객 민감 문서
퇴사자 생성 NHI → 활성 integration credential → production 데이터셋
```

### 8.3 아이덴티티 기준 자산 매핑

특정 인사 변동자가 보유한 SaaS 계정 전체와 해당 계정들이 연결된 자산을 인물 중심으로 묶어서 표시한다. 기본 탐지 흐름(8.1~8.2) 구현 후 Backlog에서 검토한다.

### 8.4 민감 자산 영향 기준 위험 설명 및 우선순위

단순히 계정이 남아 있다는 사실이 아니라, 최종 접근 가능한 자산의 민감도와 중요도 기준으로 리스크를 설명하고 우선순위를 매긴다.

#### 1. 민감도 분류 기준

- **Critical:** 개인정보보호법/신용정보법/전자상거래법에 의해 **법적으로 보호 의무가 강제되는 정보**
- **High:** 유출 시 비즈니스 **운영상 타격이 있는 핵심 자산**
  - 단, 고객 개인정보나 결제정보 접근으로 이어질 경우 Critical로 승격
- **Medium:** 사내 업무상 공유가 필요한 내부 자산

#### 2. 민감도별 자산 종류

| 카테고리 | Critical | High | Medium |
| --- | --- | --- | --- |
| 사용자 데이터 | 고객 식별 정보<br>(이름, 전화번호, 이메일)<br>주소/배송지 정보<br>개인별 주문 내역<br>개인별 결제·환불 내역 | 고객 행동 로그<br>고객 세그먼트 데이터 | 비식별 통계 데이터 |
| 금융 & 비즈니스 | 카드/계좌 정보<br>판매자 정산 정보<br>판매자 계좌/계약 정보 | 정산 및 전사 매출 데이터<br>SCM 공급가 및 계약서 | - |
| 인프라 & 기술 | - | DB 암호화 키<br>서비스 핵심 소스코드<br>운영 시스템 루트 권한 계정<br>운영 SSL/TLS 인증서 개인키<br>운영 Secret | 개발 로그<br>스테이징 환경 정보 |
| 운영 & 사내 정보 | - | 권한 목록<br>보안 감사 로그<br>운영 문서(운영 정책, 런북 등) | 입점 셀러 리스트 |

우선순위 추가 기준:
- 접근 경로가 활성 상태인지 여부
- 사람 계정인지 NHI인지 여부

MVP에서 독립적인 점수 요소로 사용하지 않는 것 (맥락 정보로는 표시 가능):
- credential 발급 경과 기간, 담당자 수, 마지막 검토일, 만료일, 갱신 지연 여부, 대체 담당자 여부

### 8.5 리스크 카드 생성

탐지된 접근권한 드리프트를 리스크 카드 형태로 제공한다.

포함 필드:
- 리스크 제목, 드리프트 유형
- 대상 계정 또는 NHI
- 접근 경로
- 민감 자산
- 왜 위험한가 / 잠재적 영향
- 잔존 접근 기간 (수개월 방치 케이스 식별용)
- 권장 조치
- 검토 담당자
- 심각도 등급
- 상태

### 8.6 조치 및 사람 승인 우선 자동화

무승인 자동 조치 없음. 리스크 카드에서 두 가지 조치로 이어진다.

**검토 요청**
- AI가 런북·정책 문서 기반으로 Jira 티켓 초안 생성 (8.7 참고)
- 보안팀 확인 후 생성 → 담당자 검토·승인

**권한 회수**
- 대상 시스템 API 호출로 실행 (사람 계정: SaaS API / NHI: Azure 등 대상 시스템 API)
- 보안팀에 관리자 권한이 있는 경우에만 가능
- 권한 회수 실행이 사람 승인으로 간주

**상태 기록**
- 리스크 수용 / 오탐 / 조치 완료 상태 기록
- 담당자 검토 요청 메시지 발송 이력 포함 (구현 우선순위 낮음)

### 8.7 AI 조치 보조

탐지된 접근 경로와 런북·정책 문서(RAG)를 기반으로 조치 문안을 생성한다. AI는 탐지 판단자가 아니라 조치 보조자다.

생성 가능:
- 리스크 요약 및 왜 위험한지 설명
- 담당자 검토 요청 메시지
- Jira/GitHub 이슈 초안
- 권한 회수·갱신 체크리스트
- 감사·보고용 요약 — 어떤 접근 경로가 탐지됐고 어떤 조치를 했는지 기록용 텍스트 생성

제약:
- 탐지 근거에 없는 유출 사실을 말하지 않는다
- secret 값을 출력하지 않는다
- "침해됨"이라고 단정하지 않는다 — "접근 가능한 경로가 남아 있음"으로 표현
- 자동 권한 회수 전에는 반드시 사람 승인

## 9. 성공 기준

**제품 성공 기준**  
데모를 본 사람이 1분 안에 다음 3가지를 말할 수 있어야 한다:
1. 어떤 권한이 남아 있는가
2. 그 권한이 어떤 중요한 자산에 닿는가
3. 다음 조치가 무엇인가

**MVP 검증 기준**
- 패턴 1, 2에 해당하는 심어진 위험을 탐지할 수 있다
- 탐지 결과가 리스크 카드로 생성된다
- 리스크 카드에 접근 경로, 민감 자산, 잔존 접근 기간이 표시된다
- 심각도 등급이 민감 자산 민감도 기준으로 설명된다
- AI 보조자가 탐지 근거 기반 티켓·메시지 초안을 생성한다
- 보안팀이 리스크 카드 상태를 변경하고 조치 내역이 기록된다

## 10. 주요 가정

**제품 가설**
- 보안팀은 계정 목록보다 "어떤 민감 자산에 닿는가"를 더 중요하게 본다. 접근 경로와 민감 자산 영향이 조치 우선순위 판단에 더 유용하다.
- SCIM/IdP만으로는 실제 SaaS/NHI 접근권한 잔존 문제를 충분히 설명하기 어렵다. 이 gap이 구조적으로 Access Drift를 만든다.
- AI Agent는 탐지 판단보다 조치 문안 생성에 더 적합하다. 이미 탐지된 근거를 바탕으로 담당자 검토 요청 메시지와 티켓 초안을 생성하는 것이 더 안전하고 유용하다.

**MVP 구현 가정**
- 민감 자산 분류는 8.4절에 정의한 Critical/High/Medium 3단계 레이블 기준을 사용
- 아이덴티티 매칭은 이메일/UPN exact match 기반으로 구현한다. alias/퍼지 매칭 기반 ER은 S2 이후 확장으로 검토한다
- 접근 이벤트/로그(audit log)는 탐지 기준으로 사용하지 않으며, 대시보드 상세분석 화면의 참고 정보로만 표시
- MVP의 최종 위험 판정은 룰베이스로 수행한다. Isolation Forest는 위험 판정에 직접 사용하지 않고 후속 비교/실험용 baseline으로 둔다
- 제한된 데모 소스(Azure App Registration, GitHub)와 사전 정의된 위험 패턴만 다룸
- 권한 제거는 사람 승인 우선 방식으로 — 버튼 클릭이 사람 승인
- 그래프는 사전 정의된 위험 경로 탐지와 접근 경로 설명용으로 사용
- AI는 판단자가 아니라 조치 보조자
